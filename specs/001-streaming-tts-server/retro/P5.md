## Decisions Made

1. **Voice validation is fatal**: Invalid voice ID or out-of-range parameters result in a fatal `session.error`, requiring the client to reconnect. This matches the existing behavior for provider errors and ensures clients correct issues immediately.

2. **Two error codes for voice issues**: `invalid_voice` for non-existent voice IDs (includes alternatives) and `invalid_voice_config` for parameter validation errors (speed/pitch/volume out of range). This provides clear error differentiation.

3. **Provider-specific voice lists**: Voice validation uses the selected provider's voice list, not a global list. This ensures voices are validated against the actual provider being used.

4. **Re-use existing VoiceConfig validation**: Leveraged the existing `VoiceConfig::validate()` method in yappy-core rather than duplicating validation logic.

## Challenges Encountered

1. **Pre-existing implementations**: Discovered that voice parameter passing (T124) and the Kokoro voice list (T126) were already fully implemented in Phase 3. The session.init handler already passed VoiceConfig to the provider, and Kokoro already had 10 voices defined. Only validation logic was missing.

2. **Mock provider voice IDs**: Integration tests initially used `test_voice` but the mock provider had `test_voice_1` and `test_voice_2`. Fixed by updating tests and adding `MockTtsProvider::with_voice()` helper.

## Learnings

1. **Check existing implementation thoroughly**: Before implementing tasks, verify what already exists. Several tasks were marked as pre-existing once the codebase was examined.

2. **Validation belongs at the boundary**: Voice validation at session.init (the boundary between client and server) catches errors early, before any audio processing begins.
