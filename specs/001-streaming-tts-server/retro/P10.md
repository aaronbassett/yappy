### Concurrent Session Support

The server must support multiple simultaneous WebSocket connections without interference between sessions.

### Requirements

- **FR-017**: System MUST handle multiple concurrent WebSocket sessions.
- **FR-018**: Each session MUST be fully isolated (buffer state, voice config, audio encoding) - no cross-contamination.
- **FR-019**: System MUST support configurable per-provider synthesis concurrency limits to prevent resource exhaustion.
- **FR-020**: System MUST implement backpressure when a session's audio output falls behind, pausing synthesis rather than buffering unbounded.

## Implementation Summary

### Bounded Channel Backpressure (FR-020)

Implemented `BackpressureSender<S>` wrapper in `ws.rs`:
- Uses `tokio::sync::Semaphore` with configurable capacity (default: 32, range: 1-256)
- Binary frames acquire a permit before sending; JSON control messages bypass backpressure
- When at capacity, synthesis naturally pauses until client consumes frames
- `BackpressureMetrics` tracks event count and total wait time
- Metrics logged at session close for observability

Configuration: `server.audio_channel_capacity` in `yappy.toml`

### Per-Provider Concurrency Limit (FR-019)

Implemented semaphore-based limiting in `ProviderRegistry`:
- Added `synthesis_semaphores: HashMap<ProviderId, Arc<Semaphore>>` for per-provider limits
- `SynthesisPermit` RAII guard ensures automatic permit release
- `acquire_synthesis_permit()` async method for blocking acquisition
- `try_acquire_synthesis_permit()` for non-blocking attempts
- Tracing logs for synthesis queuing and permit acquisition

Configuration: `providers.max_concurrent_synthesis` (default: 4, range: 1-64)

### Session Isolation (FR-018)

Verified existing implementation already provides complete isolation:

| Component | Isolation Method |
|-----------|------------------|
| Session object | Stack-local per connection |
| SentenceBuffer | Owned by Session (no Arc/Rc) |
| Voice config | Per-session field |
| Audio format | Per-session field |
| Code block mode | Per-session field |
| Audio statistics | Per-session counters |
| BackpressureSender | Per-connection with own semaphore |

Shared state is read-only: ProviderRegistry (via Arc), SRX_RULES (static), Config (cloned).

Added comprehensive documentation and debug assertions.

## Decisions Made

1. **Semaphore-based backpressure**: Chose semaphore over bounded channel because it provides better control - we can differentiate between binary audio frames (which need backpressure) and JSON control messages (which should always go through immediately).

2. **Per-provider semaphores**: Each provider gets its own semaphore rather than a global limit. This prevents a slow provider from blocking synthesis on a fast provider.

3. **Default values**: Chose 32 for audio channel capacity (middle of 32-64 range) and 4 for max concurrent synthesis (conservative default that works well for most setups).

4. **RAII permit pattern**: Using guard types ensures permits are automatically released even on panics or early returns.

## Learnings

1. **Semaphore permits as flow control**: Tokio semaphores are excellent for flow control - `try_acquire_owned()` for non-blocking and `acquire_owned()` for blocking, with `OwnedSemaphorePermit` as RAII guard.

2. **Control message bypass**: Important to let error messages and session.ready bypass backpressure so clients get timely feedback even when under load.

3. **Test design for concurrent tests**: Using `join_all` with `tokio::spawn` and proper timeouts makes concurrent tests reliable. Collecting results into Vecs and asserting after join prevents race conditions in assertions.

4. **Mock provider flexibility**: Adding `SuccessWithDelay` mode to mock providers enables realistic timing tests without needing real TTS providers.
