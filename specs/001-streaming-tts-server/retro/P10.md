## Requirements Summary

From spec.md User Story 8 and contracts/:

### Concurrent Session Support

The server must support multiple simultaneous WebSocket connections without interference between sessions.

### Requirements

- **FR-017**: System MUST handle multiple concurrent WebSocket sessions.
- **FR-018**: Each session MUST be fully isolated (buffer state, voice config, audio encoding) - no cross-contamination.
- **FR-019**: System MUST support configurable per-provider synthesis concurrency limits to prevent resource exhaustion.
- **FR-020**: System MUST implement backpressure when a session's audio output falls behind, pausing synthesis rather than buffering unbounded.

### Non-Functional Requirements

- **NFR-001**: Audio output latency MUST be < 500ms from sentence completion (P95).
- **NFR-002**: Server MUST handle 100+ concurrent sessions (P3).
- **NFR-003**: Memory usage per session MUST be < 50MB (excluding model cache).

### Success Criteria

- **SC-009**: 10 concurrent sessions complete independently without cross-contamination.
- **SC-010**: Backpressure test shows synthesis pause/resume behavior.

## Implementation Plan

### Bounded Channel Backpressure

Current implementation uses unbounded channels. Need to:
1. Change to bounded channels (32-64 frame capacity)
2. Use `send_timeout` or blocking behavior to apply backpressure
3. Track backpressure metrics in session statistics

### Per-Provider Concurrency Limit

1. Add `max_concurrent_synthesis` config to ProvidersConfig
2. Implement semaphore-based limiting in provider calls
3. Queue excess synthesis requests until slots available

### Session Isolation

1. Verify each session has its own SentenceBuffer instance
2. Verify session IDs are unique and isolated
3. No shared mutable state between sessions
